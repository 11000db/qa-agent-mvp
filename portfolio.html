// Problem

QA 노하우는 왜 팀 자산이 되지 못하는가

실무에서 요구사항 분석과 테스트 케이스 작성은 시간이 많이 들고, 사람마다 품질 편차가 큽니다. 특히 happy path 위주로만 작성되고 negative / edge case가 빠지기 쉽고, 숙련된 QA의 노하우는 개인에게만 축적되어 팀의 자산이 되지 못합니다. 이 프로젝트는 그 노하우를 재사용 가능한 에이전트로 구조화하는 것이 목표입니다.

01 요구사항 분석에 드는 시간
요구사항을 읽고 테스트 포인트를 정리하는 데만 반나절. 기능 하나에 수십 분.
02 작성자에 따른 품질 편차
누가 쓰느냐에 따라 커버리지와 표현이 달라져, 리뷰 비용이 계속 발생.
03 Happy Path 편향
Negative/Edge case가 빠져 실제 장애는 production에서 뒤늦게 드러남.
04 자동화와의 단절
TC와 자동화 코드 사이에 번역 레이어가 필요해 반영 시차가 큼.

// QA Know-how

QA 노하우가 녹아든 11개 검증 규칙

단순히 AI가 생성한 결과를 믿지 않고, QA 관점에서 "이 테스트 케이스가 실무에서 쓸 만한가"를 자동으로 검증합니다. Happy path 편향, traceability 누락, 내부 중복 같은 실제 현업에서 반복되는 품질 이슈를 코드 레벨 규칙으로 굳혔습니다.

01필수 필드 존재 여부 검사
02필수 문자열 필드 공백 여부
03필수 리스트 필드 공백 여부
04priority / risk_level 허용값 여부
05traceability 형식 여부
06negative_cases / edge_cases 교차 중복
07test_steps / expected_results 최소 개수
08traceability 내부 중복 여부
09preconditions / steps / results 내부 중복
10negative_cases 내부 중복 여부
11edge_cases 내부 중복 여부
// TC Quality Rubric · 10 criteria
01요구사항 반영 여부
핵심 기능 누락 없이 traceability가 이어지는가.
02Happy Path 포함
대표 사용자 시나리오가 빠짐없이 포함되었는가.
03Negative Case 포함
잘못된 입력·권한 없음·중복 데이터 등 실패 조건.
04Edge Case 포함
경계값·빈 값·최소/최대·특수 입력까지 고려했는가.
05Expected Result 명확성
"정상 동작" 같은 모호한 표현 대신 구체적 조건.
06Preconditions 명확성
로그인 여부·테스트 데이터·환경 조건이 분명한가.
07재현 가능성
다른 사람이 봐도 동일하게 실행 가능한가.
08우선순위·리스크
P0/P1/P2 선정에 비즈니스 영향과 장애 가능성 반영.
09자동화 적합성
Playwright/API 자동화 후보로 적절한가, 회귀 가치.
10QA 실용성
리뷰 후 바로 현업에서 사용 가능한 수준인가.
