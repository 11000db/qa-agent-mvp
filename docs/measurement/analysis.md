# 측정 결과 분석 (Day 27)

원본 결과: [measure/results/report.md](../../measure/results/report.md)

## 숫자
| 테스트 세트 | 검출률 | TC 항목 | 무효 항목 |
|------------|-------|--------|----------|
| 정상 흐름만 | 28.6% (8/28) | 15 | 2 |
| TC v1 (노하우 주입 전) | 92.9% (26/28) | 60 | 2 |
| TC v2 (노하우 주입 후) | 92.9% (26/28) | 74 | 7 |

## 발견 1. Negative / Edge 케이스가 검출률의 대부분을 만든다
정상 흐름만 자동화하면 28.6%, Negative/Edge까지 포함하면 92.9%.
로그인 결함 7개 중 정상 흐름이 잡은 건 2개(평문 노출, 이동 안 함)뿐이었다.
잘못된 비밀번호 허용(L1) 같은 치명적인 결함은 정상 흐름 테스트를 전부 통과한다.

## 발견 2. 노하우 주입(Day 24)은 검출률을 올리지 못했다
v1과 v2 모두 26/28. 대신 **무엇을** 잡는지가 바뀌었다.
- v2만 잡은 결함: **C11** (삭제 후 다시 담으면 이전 수량 복원)
  → v2의 `[Regression]` 항목(E7)이 잡았다. 노하우 주입이 의도대로 작동한 사례.
- v1만 잡은 결함: **C3** (수량 0이 제거되지 않음)
  → v2는 이 상황에 "오류 메시지 또는 확인 팝업"을 기대했다. 요구사항은 "0이면 제거"라서 이 항목은 정상 앱에서 실패하는 무효 항목이 됐고, 결과적으로 결함을 놓쳤다.

## 발견 3. 노하우 주입 후 "요구사항에 없는 기대"가 늘었다
무효 항목이 2개에서 7개로 늘었다. 계정 잠금, 로그인 페이지 자동 이동, 로그아웃 후 장바구니 유지, 이름 길이 제한 등
요구사항에 없는 동작을 사실처럼 기대했다. 이런 항목을 그대로 자동화하면 **오탐(가짜 버그 리포트)** 이 된다.
항목 수는 60 → 74로 늘었지만 측정에 쓸 수 있는 항목은 40 → 46으로 6개 늘었을 뿐이다.

## 발견 4. 기대 결과가 없는 항목이 결함을 놓치게 했다
v1, v2 모두 놓친 **S4** (대소문자만 다른 이메일 중복 가입)는 두 TC 모두 "중복 처리 확인"으로만 적혀 있었다.
무엇이 맞는 결과인지 적혀 있지 않아 판정할 수 없었다. 이런 "판정 기준 없음" 항목이 v1 6개, v2 4개였다.

## 개선 방향
1. **검증 규칙 추가**: 기대 결과 없이 "확인", "여부 확인", "처리 확인"으로 끝나는 항목을 잡는 규칙
2. **프롬프트 수정**
   - 요구사항에 없는 동작은 기대 결과로 쓰지 말고, 필요하면 `[확인 필요]` 태그로 구분
   - 모든 항목에 판정 가능한 기대 결과를 쓴다
3. 수정한 프롬프트로 TC v3를 생성하고 같은 방법으로 다시 측정 (Claude API 키 필요)

## 한계
- 결함 28개, TC 버전마다 한 번 생성한 결과다. 같은 프롬프트로 다시 생성하면 숫자가 바뀔 수 있다.
- 앱, 결함, 테스트를 모두 내가 만들었다. 결함을 테스트보다 먼저 커밋해서 순서는 증명되지만 편향이 0은 아니다.
