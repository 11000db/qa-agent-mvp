# 결함 검출률 측정 프로토콜

## 질문
AI(Claude)가 요구사항으로 만든 테스트 케이스(TC)는 실제 결함을 얼마나 잡는가?
Day 24에 넣은 QA 노하우(Knowledge Injection)는 그 비율을 올렸는가?

## 방법: 결함 주입 (mutation testing)
1. 요구사항 문서 3개만 보고 데모 쇼핑몰을 만든다 (`app/shop.py`, `/shop`)
2. 요구사항 문장 하나에 근거한 결함 28개를 정의한다 (`app/shop_faults.py`)
3. TC를 자동화 테스트로 옮긴다 (TC 항목 1개 = 테스트 1개)
4. 결함을 하나씩 켜고 테스트를 돌린다. 테스트가 하나라도 실패하면 그 결함은 "검출"
5. 검출률 = 검출한 결함 수 / 전체 결함 수

## 비교 대상 (테스트 세트 3개)
| 세트 | 내용 |
|------|------|
| 정상 흐름만 | Day 24 이후 TC의 test_steps / expected_results만 자동화 |
| TC v1 | Day 24 이전 TC 전체 (git `10acc79~1`의 sample_outputs) |
| TC v2 | Day 24 이후 TC 전체 (Knowledge Injection 적용, 현재 sample_outputs) |

## 편향을 줄이기 위한 규칙
- **순서 고정**: 앱과 결함 목록을 먼저 커밋하고, 그 뒤에 테스트를 작성한다. git 기록으로 확인할 수 있다.
- **근거 필수**: 모든 결함은 요구사항 문장 번호를 근거로 가진다. 요구사항에 없는 동작은 결함으로 만들지 않는다.
- **TC 그대로**: 테스트는 TC 문장이 기대하는 동작만 확인한다. TC에 없는 확인을 덧붙이지 않는다.
- **문구는 의미로**: TC마다 오류 문구가 조금씩 달라서, 문구 완전 일치 대신 "같은 의미의 오류가 표시되는가"를 본다.
- **무효 항목 제외**: 결함이 없는 정상 앱에서 실패하는 테스트는 TC가 요구사항에 없는 동작(예: 계정 잠금)을 가정한 것이다. 이런 항목은 측정에서 빼고 따로 집계한다. 넣으면 검출률이 부풀려진다.
- **자동화 불가 항목 집계**: DB 직접 조회, 크로스 브라우저, 네트워크 단절 등 이 데모로 확인할 수 없는 항목은 사유와 함께 집계한다.
- **절차 변환 기록**: TC 절차가 앱 정책과 다르면(예: 상세 페이지에서 수량 3개 선택) 의도를 유지하는 최소 변환을 하고 기록한다.

## 앱 정책 (요구사항에 없어서 정한 것)
`app/shop.py` 맨 위 주석 참고. 요약:
- 비로그인 장바구니 허용, 계정 잠금 없음, 로그인 페이지 자동 이동 없음
- 상품 상세에서 1개씩 담기, 수량 칸은 텍스트 입력 (서버 검증)
- 이메일은 앞뒤 공백 제거 + 대소문자 무시, 비밀번호는 입력 그대로 비교

## 한계
- 앱, 결함, 테스트를 같은 작성자(AI 보조)가 만들었다. 순서 고정과 근거 규칙으로 줄였지만 편향이 0은 아니다.
- 결함 28개는 실제 결함 분포를 대표하지 않는다. "이 앱, 이 결함 목록 기준"의 상대 비교로 읽어야 한다.
- TC v1과 v2는 각각 한 번 생성된 결과다. 같은 프롬프트로 다시 생성하면 결과가 달라질 수 있다.
