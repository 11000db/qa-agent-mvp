# Day 27 Summary: AI 생성 TC 결함 검출률 측정

## 작업 날짜
2026-11-04

## 목표
AI가 만든 TC가 실제 결함을 얼마나 잡는지 숫자로 확인한다.
Day 24에 넣은 노하우(Knowledge Injection)가 효과가 있었는지도 같이 본다.

## 배경
지금까지는 TC를 "만들고" "형식을 검증"하는 데까지만 했다.
11개 규칙을 통과해도 그 TC가 버그를 잡는지는 알 수 없다.
형식이 맞는 TC와 버그를 잡는 TC는 다르다.

## 방법: 결함 주입
1. 요구사항 문서 3개만 보고 데모 쇼핑몰을 만들었다 (`app/shop.py`, `/shop`)
2. 요구사항 문장 하나에 근거한 결함 28개를 정했다 (`app/shop_faults.py`)
3. 결함 목록을 먼저 커밋했다 (`b7fece0`). 테스트를 쓰면서 결함에 맞추는 걸 막기 위해서다.
4. TC v1(Day 24 이전)과 v2(이후)를 항목 1개 = Playwright 테스트 1개로 옮겼다 (`c60db09`)
5. 결함을 하나씩 켜고 테스트를 돌렸다. 하나라도 실패하면 검출.

## 결과
| 테스트 세트 | 검출률 | 무효 TC 항목 |
|------------|-------|-------------|
| 정상 흐름만 | 28.6% (8/28) | 2 |
| TC v1 | 92.9% (26/28) | 2 |
| TC v2 | 92.9% (26/28) | 7 |

## 알게 된 것
- 정상 흐름만 테스트하면 잘못된 비밀번호로 로그인되는 결함도 통과한다. Negative / Edge가 검출의 대부분을 만든다.
- 노하우를 넣어도 검출 수는 같았다. 대신 v2는 Regression 항목으로 C11(삭제 후 다시 담으면 이전 수량 복원)을 잡았고, v1이 잡은 C3(수량 0 미삭제)는 놓쳤다.
- v2는 요구사항에 없는 동작(계정 잠금, 로그아웃 후 장바구니 유지 등)을 기대하는 항목이 2개에서 7개로 늘었다. 그대로 자동화하면 가짜 버그 리포트가 된다.
- 둘 다 놓친 S4(대소문자만 다른 이메일 중복 가입)는 TC에 "중복 처리 확인"으로만 적혀 있었다. 기대 결과가 없으면 판정을 못 한다.

## 측정하면서 고친 것
- 폼 제출 직후 이전 페이지를 보고 판정하는 문제가 있었다. "로그아웃 상태" 확인이 옛 화면을 보고 통과하면 결함을 놓친다. 새 페이지 로드까지 기다리도록 바꿨다.
- 결함 없이 두 번 돌려서 결과가 다르면 측정을 멈추게 했다. 불안정한 테스트가 섞이면 숫자를 믿을 수 없다.
